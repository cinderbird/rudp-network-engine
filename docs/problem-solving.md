# 문제 해결 과정 — Toska RUDP 엔진

## 한눈에 보기

| # | 문제 | 분석 | 지표 |
|---|---|---|---|
| 1 | 여러 테스트에서 아주 드물게 발생하는 서버 크래시 | 상관과 인과의 분리, 음성 대조군 설계 | 동시성을 **전부 제거**했는데도 11/20 재현 → 재현율 35% → **0%** |
| 2 | Job 시스템 변경에 따라 변동하는 Handshake 성공율 | 추정을 결론으로 굳히지 않기, 계측 우선 | 커넥션 4배에 Job **14.4배**(사실상 O(N²)) → 핸드셰이크 54.2% → **99.2%** |
| 3 | 측정 지표에서 보이는 이상치 | 지표 타당성 검증, 자기 과거 데이터 강등 | 실제 20/20인데 지표는 **9/20** — 엔진이 빨라질수록 나빠 보이는 역방향 계측 |

### 오류 탐지 경로

- **크래시** — 2건
- **모순적인 지표** — 1건 
- **코드 테스트** — 3건
- **코드 검토** — 1건
- **예측 결과와 다른 값** — 3건

**절반 이상이 크래시 이외의 경로로 발견되었습니다.**

## 이 프로젝트의 문제 해결 절차

1. **문제 재현** 개선/해결 전 지표를 측정하여 전후 비교를 수행합니다.
2. **가설과 결과.** 가설을 세우고 결과로 검증합니다. 문제를 해결할 때까지 반복합니다.
3. **변수를 통제.** 한번에 하나씩 검증합니다.
4. **데이터가 가설이 일치할 때, 반증을 한 번 더 시도합니다.** 결과만 가지고는 문제가 완전히 해결되었다고 볼 수는 없습니다.
5. **문서화** 비슷한 문제를 마주할 때, 참고하기 좋은 문서를 작성합니다.

## 사례 1 — 아주 드물게 발생하는 서버 크래시

| | |
|---|---|
| **발견** | 스레드 안전성 검증 중 |
| **탐지 경로** | **크래시** — 부하 테스트에서 클라이언트 프로세스가 Assert로 종료. 재현율 3~13/20 |
| **상태** | 아주 드물게 발생하는 버그임으로 초기에 탐지 실패, 여러 컴포넌트가 구현된 상황 |
| **관련 결정** | [결정-0001](decisions/0001-connection-worker-pinning.md) |

### 증상

부하 테스트(20클라이언트/45초/10% 손실)를 돌리면 클라이언트 프로세스 일부가
`ChannelRecord.h:39`의 Assert에서 죽었다. 재현율은 실행마다 3/20에서 13/20으로 변동성이 심했다. Assert의 위치는 멀티스레드 네트워크 코드 — **"데이터 레이스"를 첫 가설로 설정**

### 가설을 시험할 방법 설계

레이스라면 동시성을 줄일수록 재현율이 낮아져야 한다. IOCP 스레드 수를 2 → 1로 낮췄다.
결과 — **6/20, 13/20으로 오히려 심해졌다.**

그때까지 확보해 둔 모든 실행의 수치를 정리, 두 변수(스레드 수 × 틱 속도)로 정리.

| 실행 | 스레드 수 | 틱 | 재현 |
|---|---|---|---|
| 072418 | 2 | 60Hz 쓰로틀 | **0/20** |
| 072924 | 2 | 60Hz 쓰로틀 | **0/20** |
| 072744 | 2 | 무제한 | **12/20** |
| 073254 | 1 | 무제한 | 6/20 |
| 073409 | 1 | 무제한 | 13/20 |

**스레드 수와 무관하게 틱이 무제한이면 Assert를 재현.** 상관을 갖는 변수는 스레드 수가 아니라 초당 처리량.

### 대조군 — 동시성을 완전히 제거

**틱 풀과 워커 풀을 둘 다 정확히 1개**로 축소 — 
결과 — 11/20, 3/20으로 재현. 

결론 — 레이스 가설 폐기, "타이밍과 락"에서 "로직"으로 조사 방향 전환

### 실제 원인

디버거를 준비하는 대신 `AssembleOutgoingPackets()`를 끝까지 추적. 원인은
`else` 분기에서 `Packet`을 초기화하지 않은 것이었다.

```cpp
if (Packet->TotalSize + RequireSize > ConnectionPacketBuilder::PacketMaxSize)
{
    OutPacketId++;
    Packet->PacketSealed();
    readyPackets.push_back(Packet);

    if (Channel->HasReadyBunch()) { Packet = createNewPacket(); }
    else                          { break; }   // Packet이 그대로 남는다
}
```

이 한 줄의 누락이 **세 가지 서로 다른 실패**를 동시에 만들었다.

1. 다음 채널이 `Packet != nullptr`을 보고 새 패킷을 만들지 않아, **이미 큐에 들어간
   "봉인된" 패킷을 사후에 계속 변형**.
2. 함수 끝의 "마지막 패킷 확정" 블록이 **같은 `shared_ptr`을 두 번째로 push**
3. 오버플로를 유발한 그 Bunch 자체가 어떤 패킷에도 담기지 못하고 **유실**.

같은 패킷이 물리적으로 두 번 전송되면 `ConnectionChannelRecord`는 마커를 하나만
남기는데(중복 제거) 실제 `OutSeq`는 두 번 증가 — 이 어긋남이 누적되어 Assert 발생.
**관측된 모든 특징(스레드 수와 무관, 처리량과 상관)이 확인.**

### 수정과 검증

`else { break; }`를 없애고 오버플로 시 항상 새 패킷을 시작하게 하면, 손에 든 Bunch는 항상 새 패킷에 담기고 내부 루프는
`DequeueReadyBunch`가 false를 반환하며 종료.

| | 수정 전 | 수정 후 |
|---|---|---|
| 재현 | 14 / 40 시도 (**35%**) | **0 / 60 시도 (0%)** |

### 완전히 해결하지 못한 의문

**"왜 시퀀스 추적과 채널 레코드 큐가 어긋나는가".** 

크래쉬가 터진 워커 스레드는 실행 환경에서 응답 없는 `MessageBoxW` 안에 영원히
멈춘다. 그런데 커넥션-워커 고정에 의하여 **그 워커를 공유하는 다른 모든 커넥션이 같이
멈췄다** — 크래시한 프로세스의 로그가 125줄의 `Reason=Timeout` 로그 확인. 

의문에 대한 두 가지 고찰.

**첫째, 디버깅 방법 변경.** cdb로 프로세스를 처음부터 띄우면 디버거 오버헤드가 타이밍을 바꿔 재현에 계속 실패.
그래서 **`Assertion failed`가 찍히는 순간에만 사후 attach**했다 — 

**둘째, 신뢰성 보장 로직의 안전성.** `RELIABLE_BUFFER`의 오버플로 발생 시 조기 return과, 이미 큐에 들어가 있던 stale Ack/Nack Job의 상호작용은 순서
재배치를 추가하여 예상치 못한 에러 발생에 대하여 각 쓰레드가 담당하는 모든 커넥션이 강제 종료되는 상황을 방지

| | 수정 전 | 수정 후 (동일 조건 3회) |
|---|---|---|
| 프로세스 크래시 | 8개 중 5개 | **0건** |
| 디싱크 발생 자체 | — | 5건 / 3건 / 2건 (여전히 발생) |
| 피해 반경 | 125커넥션 | **1커넥션** |

> **크래쉬가 남아 있는 이유**
테스트 과정에서 의도적으로 특정 연결을 죽이는 테스트를 수행, 크래시는 예상된 결과

## 사례 2 — "Job 시스템 변경에 따라 변동하는 Handshake 성공율

| | |
|---|---|
| **발견** | M16, 스케줄러(busy-spin vs CV-wait) 평가 중 |
| **탐지 경로** | **의도한 실험** — 부하 × 반복 매트릭스에서 부하가 오를수록 CV-wait만 나빠지는 것을 관측 |
| **상태** | 테스트 코드에 따라 발생하는 문제로 판단하였지만, 이후 여러 테스트 과정에서 해당 판단이 틀렸음을 확인. |
| **관련 결정** | [결정-0002](decisions/0002-cv-wait-scheduler.md), [결정-0004](decisions/0004-tick-io-separation.md) |

### 배경

JobSystem 워커의 대기 방식을 busy-spin에서 CV-wait으로 바꾸면 CPU를 크게 아낄 수 있는데,
부하가 올라갈수록 핸드셰이크 성립률이 떨어졌다(40커넥션에서 54.2%).

원인 후보를 하나씩 검증하며 제거.

- 클라이언트를 잃어버린 핸드셰이크 문제 해결 → 63.8%로 개선. 여전히 낮은 Handshake 성공률.
- `Internal_AddJob`에서 lost-wakeup 레이스를 찾아내어 개선 → 재측정 결과 유의미한 변환 없음.
- 워커 스레드의 OS 우선순위를 올림 → **악화(63.8% → 48.8%)**. 

### 측정과 개선

20커넥션에서 틱 루프가 초당 수천 번 돌 거라 예상했는데 실제로는 88Hz. `완료 78 + 타임아웃 10 = 88`. **GQCS의 100ms 타임아웃이 우연히 루프를 쓰로틀.**

확실하게 확인하기 위해 커넥션을 4배로 증가.

| | 20커넥션 | 80커넥션 | 배율 |
|---|---|---|---|
| GQCS 타임아웃/초 | 10 | **0~5** | 붕괴 |
| 틱/초 | 88 | 319 | 3.6× |
| 총 Job/초 | 3,557 | **51,191** | **14.4×** |
| 실제 패킷 작업 | 37 | 151 | 4.1× (선형) |
| 낭비 비율 | 95 : 1 | **339 : 1** | |

결과: 커넥션↑ → 패킷↑ → **타임아웃이 0으로 붕괴** → 루프를 막던 유일한
브레이크가 사라짐 → 틱레이트 상승 → 스윕 Job(`N × 틱레이트 × 2`)이 폭증. 사실상 O(N²)다.

## 측정을 통해 찾은 문제

`Internal_AddJob`은 enqueue마다 `notify_all()`로 **모든워커를 기상**, 그 Job은 핀 고정에 의해 **특정 워커의 로컬 큐**에만 들어간다 — 80커넥션이면 초당 약 20만 회 기상 중 15만
회가 불필요한 기상, **busy-spin에서는 거의 공짜지만 CV-wait에서는 전부 커널을 호출**
"부하가 올라갈수록 CV-wait 성능 감소" 원인을 설명. 

### 수정 — 한 번에 하나씩

| 조치 | 내용 | 측정(성공률) |
|---|---|---|
| P3 | 전역 CV/뮤텍스 → **워커별 신호**(정확히 그 워커만 기상) | 63.8% → **80.8%** |
| P1 | `IOCPDispatch`를 **소켓 드레인**과 **정주기 스윕**으로 분리 | 틱 319 → **60Hz**, Job 51,191 → **9,750**, 핸드셰이크 67~77/80 → **80/80** |
| P2 | `GetQueuedCompletionStatusEx` 배치 dequeue(최대 64건) | 버스트 시 커널 전이 감소 |

### 최종 결과

| 시점 | CV-wait 핸드셰이크율 |
|---|---|
| 최초 실측 | 54.2% |
| 이슈 수정 + lost-wakeup 수정 | 63.8% |
| P3 (워커별 기상) | 80.8% |
| **P3+P1+P2** | **99.2%** |

CPU는 busy-spin 197.9% 대비 **2.3%** — 신뢰성을 지키면서 CPU 소모를 약 86배 개선.

## 사례 3 — 측정 지표에서 보이는 이상치

| | |
|---|---|
| **발견** | 최종 검증 중 |
| **탐지 경로** | **지표 모순** — 코드를 개선했는데 수치가 급락. 서버 로그와 교차 검증해 계측 오류로 판명 |
| **상태** | 기존에 확인한 모든 문제점은 해결된 상황. |
| **관련 결정** | [결정-0003](decisions/0003-telemetry-opt-in.md) |

### 개선했더니 지표가 나빠졌다

최종 검증 결과, 핸드셰이크 수치가 20/20에서 **9/20, 6/20, 11/20**으로 급락.

여러 지표를 점검 — 잔여 프로세스 0, CPU 21%, UDP 소켓 76개(고갈 아님), RAM 여유,
로그 파일 크기 정상.

 **서버 로그를 직접 세어보니 서로 다른 ConnectionId 20개가 전부 정상 처리**
결과: 성능 저하가 아니라 **측정 오류**.

원인: 로깅 설정에 따른 문제 발생.

1. 모든 클라이언트 프로세스가 **같은 로그 파일에 쓴다.** `daily_file_sink_mt`는 프로세스
   *내* 스레드 안전일 뿐, 프로세스 간 잠금이 없다.
2. 비동기 로거가 `overrun_oldest` + 1만 개 큐 + trace 전량 로깅이라, **큐가 넘치면 가장
   오래된 메시지를 조용히 삭제**

즉 **앞서 성능 개선에 따라 엔진이 빨라져 핸드셰이크가 짧은 구간에 몰릴수록 로그 유실이 심해진다. 이에 따라 지표가 더 나빠
보인다.** 

측정관련 문제를 해결하며 같은 성질의 결함을 세 개 더 발견.

- **로그 레벨이 `trace`로 하드코딩.** 수신 패킷마다 DEBUG 두 줄 — 초당 2만 패킷이면
  4만 줄/초. 위 유실을 가속하는 원인.
- **Windows는 스레드 CPU를 15.625ms 단위로만 회계.** 가벼운 워커의 1초 샘플은 0 또는
  0.0156만 나옴 — 관측값이 전부 15,625의 배수.
- **지표가 `info` 로그 파싱.** 로그 레벨을 내리면 조용히 0. 초당 1,308패킷으로
  20커넥션을 정상 서비스하던 실행이 0/20으로 보고.

**세 결함의 공통점: 잘못 측정한 결과를 전송.**

### 결과
| # | 개선 | 확인된 효과 |
|---|---|---|
| 1 | **확인된 지표 도입** — 서버 로그의 고유 ConnectionId 수를 센다 | 실제 성립 수가 처음으로 정확히 보임. 기존 클라이언트측 지표는 "하한"으로 강등 표기 |
| 2 | **`LogLevel` 설정 추가** — 로거의 `trace` 하드코딩 제거 | 초당 4만 줄이 큐를 넘치게 하던 원인 제거 (기본값은 기존 동작 유지) |
| 3 | **로그 파일에 PID 접미사** | 프로세스 간 파일 공유 유실 경로 자체가 사라짐 → 같은 지표가 **3회 연속 20/20** |
| 4 | **상설 `stats` 전송** | 측정 경로가 로그와 분리됨.|
| 5 | **CPU를 전체 구간 누적 카운터로 계산** | Windows의 15.625ms 스케줄러 틱 양자화를 우회 |
| 6 | **지표 무력화 시 명시 출력** | 로그 기반 지표가 0이면 "실패가 아니라 구조상 0"이라고 표시 |

### 배운 점
