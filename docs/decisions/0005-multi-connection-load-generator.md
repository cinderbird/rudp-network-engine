# 결정-0005: 부하 생성기를 프로세스당 N 커넥션으로

| | |
|---|---|
| **근거** | 측정 결과 CPU 11.2배 / 메모리 27.6배 절감 |
| **관련** | [결정-0001](0001-connection-worker-pinning.md) |

## 배경

`RemoteServer.exe` 하나가 커넥션 하나였다. 즉 **커넥션 수를 늘리는 것 = OS 프로세스 수를
늘리는 것.** 

- **부하 생성 비용이 측정 대상을 압도.** 클라이언트 합산 2.38코어 vs 서버 0.28코어 —
  **8.5 : 1**. 12코어 머신에서 서버를 포화시키기 전에 부하 생성 쪽이 먼저 포화.
- **"워커를 늘리면 처리량이 오르는가"에 답할 수 없었다.** 워커 1개조차 포화시키지 못해
  (0.537코어) 곡선이 평평한 이유가 "병렬성 실패"인지 "부하 부족"인지 구분 불가.
  
## 결정

**`RemoteServer.exe <N>` — 프로세스 하나가 N개의 독립 커넥션을 호스팅한다.**
N개의 `NetworkService` + `ThreadManager` 쌍을 만들어, 각자 소켓 1개와 커넥션 1개를 가진
독립 드라이버 N개가 한 프로세스에 존재.

## 근거

**엔진 코드에 준비되어 있었다.** 클라이언트 쪽 커넥션 식별자를 그 소켓 자신의 로컬 ephemeral
포트(`getsockname()`)로 쓰도록 만들어 둔 상태 — 한 프로세스 안에서 소켓마다 겹치지 않는 값.

**측정**: 같은 커넥션 수 기준 CPU **11.2배**, 메모리 **27.6배** 절감. 40커넥션이 86스레드
/35.5MB로, 이론치보다 훨씬 낮게 측정.

## 결과
이번 결정에 따른 장단점

**장점**
- 750커넥션 이상의 실규모 부하가 가능. 이를 발판으로 워커 수·IOCP 스레드 수 스케일링
  실험이 처음으로 성립.
- 웹 시각화의 "+1000개 한번에"가 프로세스 1000개가 아니라 10개로 처리.
- **클라이언트 프로세스가 서버와 같은 구조가 됐다** — 프로세스 하나, JobSystem 하나,
  커넥션 여럿.

**단점**
- `JobSystem`이 프로세스 전역 싱글턴이라 **한 프로세스의 N개 커넥션이 워커 풀을 공유.**
