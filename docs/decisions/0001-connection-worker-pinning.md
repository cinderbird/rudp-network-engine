# 결정-0001: 커넥션을 JobSystem 워커에 고정

| | |
|---|---|
| **근거** | 측정을 통해 얻은 84,016줄 로그 |
| **관련** | [결정-0003](0003-telemetry-opt-in.md), [문제 해결 과정 사례 1](../problem-solving.md) |

## 배경

`NetConnection`의 내부 상태(`OutBunchQueue`, `OutUnAckedBunches`, `InUnreadBunchMap`,
`NetPacketNotify`의 시퀀스 값, `ConnectionChannelRecord`)는 **락으로 보호되지 않는다.**
안전한 이유 — 그 커넥션의 모든 Job이 항상 같은 스레드에서 순차 실행.

## 결정

**커넥션마다 워커 하나를 배정하고, 그 커넥션의 모든 Job을 그 워커의 로컬 큐로만
보낸다.** 배정은 라운드로빈. 커넥션 내부 상태에는 락을 추가하지 않는다.

## 근거

락을 추가하는 대안과 비교했을 때, 핀 고정은 **Lock 비용이 0**. 패킷당
수십 회 발생하는 상태 접근 전부에 뮤텍스를 거는 것은 성능 저하 유발.

커넥션 ID + 배정된 워커 ID + 실제 OS 스레드 해시를 세 곳의 Job 제출 지점에서 측정.
20개 커넥션을 4개의 실제 병렬 워커로 데이터 수집

**84,016개의 데이터**.

- 20개 커넥션 × 3종류 Job 전부에서 **스레드 위반 0건**
- 20개 커넥션이 4개 워커에 정확히 5개씩 분배

## 결과
이번 결정에 따른 장단점

**장점**
- 커넥션 내부 상태에 대한 락 없는 안전성. 워커 수를 자유롭게 올릴 수 있다.
- 병렬성을 확보함으로 서버 확장에 유연하다.

**단점**
- **부하 분산이 커넥션 단위로 고정된다.** 무거운 커넥션이 한 워커에 몰려도 재분배가 없다.
- **핀 고정은 "그 커넥션의 Job들끼리"만 직렬화한다.** 해당 부분 이외에는 쓰레드 안전을 보장하지 않는다.
