# 결정-0004: 소켓 완료 꺼내기와 커넥션 관리를 분리한다

| | |
|---|---|
| **근거** | 임시 계측으로 원인 규명, 조치별 개별 측정 |
| **관련** | [결정-0001](0001-connection-worker-pinning.md), [결정-0002](0002-cv-wait-scheduler.md), [문제 해결 과정 사례 2](../problem-solving.md) |

## 배경

바깥 루프가 `IOCPDispatch()` 하나를 무제한으로 호출했고, 그 함수가 **성격이 정반대인 두 일**을
같이 하고 있었다.

| 하는 일 | 요구 주기 |
|---|---|
| 소켓 완료 꺼내기 (`GetQueuedCompletionStatus`) | 패킷이 오는 만큼 — 무제한 |
| 전 커넥션 관리 (`TickDispatch` / `TickFlush`) | 고정 주기 — `MaxTickRate` |

두 책임이 묶여 있어 **커넥션 관리 주기가 패킷 도착 속도에 종속.** 이 구조 때문에 이전에 시도한
틱 쓰로틀은 소켓 처리까지 함께 느려지게 만들어 롤백됐다.

## 결정

세 가지를 **한 번에 하나씩** 적용하고 각각 측정.

1. **워커별 기상** — 전역 뮤텍스/CV/카운터를 워커별 신호로 교체. Job이 어느 워커의 큐로 갈지
   push 전에 알고 있으므로 **그 워커만** 깨운다.
2. **틱-IO 분리** — `IOCPDispatch()`를 `PumpIO(TimeoutMs)`(무제한 처리)와
   `TickHousekeeping()`(정주기)으로 분리. 상위 루프가 자체 스케줄로 돌고,
   **다음 틱까지 남은 시간만큼만** IO에서 대기.
3. **배치 처리** — `GetQueuedCompletionStatusEx`로 호출당 최대 64건.

## 근거

임시 카운터를 넣고 먼저 측정. — 20커넥션에서 틱이 초당 수천 번 돌 거라 예상했지만 실제는 88Hz.

커넥션을 4배로 올린 결과.

| | 20커넥션 | 80커넥션 | 배율 |
|---|---|---|---|
| GQCS 타임아웃/초 | 10 | 0~5 | **붕괴** |
| 틱/초 | 88 | 319 | 3.6× |
| 총 Job/초 | 3,557 | 51,191 | **14.4×** |
| 실제 패킷 작업 | 37 | 151 | 4.1× (선형) |

커넥션↑ → 패킷↑ → **타임아웃 0으로 붕괴** → 루프를 막던 유일한 브레이크 소멸 → 틱레이트
상승 → Job(`N × 틱레이트 × 2`) 폭증. 사실상 O(N²).

**조치별 측정**

| 조치 | 측정 |
|---|---|
| 워커별 기상 | CV-wait 핸드셰이크 63.8% → **80.8%** |
| 틱-IO 분리 | 틱 319 → **60Hz**, Job 51,191 → **9,750**, 80커넥션 핸드셰이크 67~77/80 → **80/80** |
| 배치 처리 | 버스트 시 커널 호출 감소 |

## 결과
이번 결정에 따른 장단점

**장점**
- `MaxTickRate`를 통해 관리.
- [결정-0002](0002-cv-wait-scheduler.md)의 잔여 성능 저하가 대부분 해소(99.2%).
- 유휴 시엔 길게 대기, 바쁠 땐 짧게 반환 — 두 경우 모두 관리 주기는 정시 유지.

**단점**
- 상위 루프가 자체 스케줄(`NextTickTime`)을 관리해야 한다.
